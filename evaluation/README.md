# 두리번 자연어 파싱 평가 파이프라인

LLM(Gemini) **도입 전** 규칙·키워드·점수 기반 파서와 **도입 후** Gemini 의미 해석
방식을 **동일한 테스트셋**으로 비교·측정하는 재현 가능한 평가 도구입니다.
모든 수치는 실제 코드 실행 결과에서만 나오며, 임의 보정이나 과장이 없습니다.

## 무엇을 측정하나

같은 자연어 명령 80개를 두 방식에 똑같이 넣고, 각 방식이 **출발지(origin)**·
**목적지(destination)** 를 얼마나 정확히 뽑는지 비교합니다.

- **출발지 정확도 / 목적지 정확도 / 쌍 정확도**(둘 다 맞은 비율)
- **카테고리별 정확도**: 정식명칭 / 줄임말 / 표기변형 / 자연어
- **개선폭**: %p 차이, 상대 개선율, 오류 감소율(error reduction)
- **불필요한 재질문율**(Unnecessary Clarification Rate): 사용자가 출발지를 이미
  말했는데도 "지금 어디 계세요?"를 되묻는 비율
- **Gemini 응답시간**: 평균 / 최소 / 최대 / 중앙값 / p95
- **인프라 오류**(API 오류·타임아웃)와 **인식 실패**를 구분해 집계

## 파일 구성

| 파일 | 설명 |
|------|------|
| `duribeon_data.js` | `BUILDINGS`/`ORIGINS`/`SYNONYM` — 프로덕션 `src/CNUNavigator.jsx`에서 **verbatim 추출**한 데이터(값만 복제, 로직 없음) |
| `legacy_parser.js` | Gemini 도입 직전 커밋(`260d8e5`)의 규칙·점수 파서 그대로 + `parseWithLegacyParser()` 래퍼 |
| `gemini_parser.js` | 프로덕션 `api/chat.js` 핸들러를 그대로 호출(`mode:"parse"`). 응답시간·재시도·타임아웃·에러분류 포함 |
| `normalize.js` | 채점 전용 정규화기. 시스템이 출력한 이름을 캠퍼스 표준명으로 canonical화 |
| `test_cases.json` | 80개 테스트 명령(4개 카테고리 × 20) — 실제 건물/출발지 데이터로만 구성 |
| `build_testset.mjs` | 테스트셋 생성기(+자기검증). 표기 다양화 시 재실행용 |
| `evaluate.js` | 오케스트레이터. 지표 계산·CSV/JSON 출력·보고서 문장 생성 |
| `results/` | 산출물: `evaluation_results.csv`(케이스별), `summary.csv`(지표), `summary.json`(전체+보고서문장) |

## 실행 방법

```bash
# legacy만 — API 키 불필요, 완전 오프라인 (기존 방식 기준선 즉시 확인)
node evaluation/evaluate.js --legacy-only
# 또는
npm run evaluate:legacy

# legacy + Gemini 전체 평가 — GEMINI_API_KEY 필요
GEMINI_API_KEY=발급받은키 node evaluation/evaluate.js
# 또는 .env 에 GEMINI_API_KEY=... 를 넣고
npm run evaluate
```

옵션:

| 플래그 | 의미 |
|--------|------|
| `--legacy-only` / `--gemini-only` | 한쪽만 평가 |
| `--deterministic` | Gemini를 `temperature:0` 경로로 호출(재현성). 프로덕션 파일은 수정하지 않음 |
| `--runs=3` | 3회 반복 실행 후 쌍 정확도 평균±표준편차로 변동성 확인 |
| `--delay=300` | Gemini 호출 간 간격(ms, 기본 250) — 레이트리밋 완화 |
| `--limit=10` | 앞 10개만 빠르게 점검 |

> `GEMINI_API_KEY`는 프로덕션과 동일하게 서버 측 환경변수로만 사용됩니다.
> `.env` 는 `.gitignore` 대상이니 키를 커밋하지 마세요.

## 기존 방식(legacy) 기준선 — 실측값

`node evaluation/evaluate.js --legacy-only` 실행 결과(80개 명령 기준):

| 지표 | Legacy |
|------|-------:|
| 출발지 정확도 | 25.0% |
| 목적지 정확도 | 87.5% |
| 쌍 정확도 | 22.5% |
| 불필요한 재질문율 | 68.8% |

카테고리별 쌍 정확도: 정식명칭 55% · 줄임말 20% · 표기변형 10% · 자연어 5%.

해석(주의: 80개 테스트 명령 기준): 기존 방식은 **목적지**는 별칭·점수 매칭으로
비교적 잘 찾지만(87.5%), **출발지**는 교문·도서관·1학 같은 등록된 출발지 키워드만
인식하도록 설계돼 있어 "공4에서…", "인문대에서…"처럼 **건물이 출발지로 오는 문장**을
거의 놓칩니다(25%). 그 결과 출발지를 되묻는 재질문이 잦고(68.8%), 쌍 정확도가
크게 낮아집니다. Gemini 측 수치는 `GEMINI_API_KEY`를 설정해 전체 평가를 돌리면
같은 표에 채워집니다.

## 공정성 설계 (중요)

이 비교가 "기존 방식을 일부러 못하게 만든" 것이 아님을 보장하기 위한 장치들:

1. **동일 알고리즘 재현**: `legacy_parser.js`의 매칭 엔진·`findOriginInText`·
   `splitFromTo` 는 Gemini 도입 직전 커밋에서 그대로 옮긴 것입니다. 도입 후
   개선사항(Gemini·새 fallback 등)을 섞지 않았습니다.
2. **데이터 상수 고정**: 두 방식 모두 동일한 `BUILDINGS`/`ORIGINS`/`SYNONYM`을
   씁니다. `SYNONYM`·매칭 엔진·건물명 집합은 도입 전 커밋과 **바이트 단위로 동일**함을
   확인했습니다(도입 후 추가된 건 좌표/호실 정보뿐). 즉 변하는 변수는 "파싱 방식"
   하나뿐입니다.
3. **정규화기는 채점기**: `normalize.js`는 각 시스템이 **실제로 출력한** 이름만
   표준화합니다. 정답을 보고 예측을 끌어당기지 않고, legacy가 애초에 못 뽑은 값(null)은
   정규화로도 살아나지 않습니다. 두 시스템에 완전히 동일하게 적용됩니다.
4. **정규화 강도 제한**: `공과대4호관`(‘학’ 누락)·`자연과학대 1호관`·`농생대`처럼
   `SYNONYM`/별칭에 없는 표현은 정규화기도 일부러 해석하지 않습니다. 이는 프로덕션의
   실제 grounding(`smartSearch`)에서도 안 풀리는 표현이라, "시스템이 스스로 표준화해
   출력해야 정답"이 되도록 한 것입니다(기존 실패를 숨기지 않음).
5. **temperature**: 프로덕션 `api/chat.js`의 parse 모드는 temperature를 설정하지
   않아 Gemini 기본값을 씁니다. 재현성 실험이 필요하면 `--deterministic`(temp=0)을
   쓰되, 프로덕션 파일은 수정하지 않습니다.
6. **오류 구분**: API 오류·타임아웃은 인식 정확도 분모에서 제외하고 건수로 따로
   보고합니다. JSON 파싱 실패·잘못된 추출은 인식 실패(오답)로 처리합니다.

## 주의사항

- 모든 주장은 **"80개 테스트 명령 기준"**으로 한정해 해석해야 합니다. 표본이
  캠퍼스 전체 이용 패턴을 대표한다고 과장하지 마세요.
- 수치는 실행 시점의 Gemini 응답에 따라 달라질 수 있습니다(기본 모드는 비결정적).
  보고서에는 실행 일시와 `--runs`·`--deterministic` 여부를 함께 남기는 것을 권장합니다.
- 프로덕션 동작을 바꾸지 않습니다. 추가한 것은 `package.json`의 `evaluate` 스크립트와
  독립적인 `evaluation/` 폴더뿐입니다.
